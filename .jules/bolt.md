## 2026-02-19 - Regex Compilation Overhead inside Inner Loops
**Learning:** Calling `re.compile` within tight parsing loops (like inside BeautifulSoup's `find_all` checks in `src/ts4k/core/normalize.py`) carries significant overhead. Python's internal regex caching isn't fast enough to avoid this bottleneck in loops analyzing large HTML structures. Module-level pre-compiled regex objects provide measurable (~1.5x) speedups for functions like tracking pixel removal.
**Action:** Always pre-compile frequently used regular expressions at the module level rather than inside functions to optimize performance, especially when they are used within loops or BeautifulSoup callbacks.
## 2026-02-24 - Substring Search vs Compiled Regex OR
**Learning:** For simple substring inclusion checks (e.g., checking if a URL contains any of a list of indicator strings like tracking domains), using Python's generator expression `any(ind in target for ind in indicators)` is often slightly faster than compiling and searching a large combined regex `OR` pattern (e.g., `(?:a|b|c)`). Python's native `in` operator for strings is highly optimized in C. However, for full regex matching/searching against lists of complex `re.compile()` objects, combining them into a single pattern with the `|` (OR) operator provides significant (~2-3x) speedups.
**Action:** Use combined regex `OR` patterns to replace loops over multiple compiled regexes. Avoid replacing simple `any(a in b)` substring loops with regex unless the patterns are complex enough to warrant it.
## 2026-02-27 - Regex Combine Optimizations and Edge Cases
**Learning:** While concatenating regexes with `(?:pattern1)|(?:pattern2)` offers significant performance gains over a Python loop, it requires extreme care. Combining patterns breaks if any pattern contains backreferences (like `\\1`) because capturing group IDs shift. It also causes unhandled exceptions in Python 3.11+ if any pattern contains inline global flags like `(?m)`. Furthermore, exceeding complexity limits throws `re.error`.
**Action:** When combining regex patterns, always defensively check for `(?` (inline flags) and `\\[1-9]` (backreferences) and fallback to individual pattern matching. Always wrap the combined `re.compile()` in a try/except block to handle complexity/size limit exceptions gracefully.
## 2026-02-24 - Regex vs Split/Join for Whitespace Collapse
**Learning:** For collapsing multiple whitespaces into a single space, the native string method `" ".join(string.split())` is approximately 3x faster than using a compiled regular expression `re.sub(r"\s+", " ", string)`. The native string `split()` method handles all whitespace characters without arguments and handles leading/trailing whitespaces inherently, making `strip()` redundant as well.
**Action:** Replace `value.strip()` and `re.sub(r"\s+", " ", value)` combinations with `" ".join(value.split())` for faster string whitespace normalization.
## 2026-08-09 - Regex Pre-compilation and Combining OR Patterns
**Learning:** In string heavy parsing environments like `ts4k`, pre-compiling simple repetitive patterns such as `re.sub(r"[ \t]+$", "", text, flags=re.MULTILINE)` and caching them globally leads to reliable ~1.5x speed improvements. Combining two independent simple patterns such as replacing both `\s*\(<mailto:[^)]+>\)` and `<mailto:[^>]+>` with the same target string into a single OR pattern `\s*\(<mailto:[^)]+>\)|<mailto:[^>]+>` yields an even greater ~25% speedup by reducing the number of passes over strings. Also, allocating a tuple `("a", "b")` instead of a list `["a", "b"]` for `any()` checks results in slight overhead reductions.
**Action:** Always pre-compile regexes at the module-level for hot-paths and consider combining simple, non-capturing patterns targeting the same replacements into single OR expressions to reduce traversal overhead. When checking constant literal collections, always use tuples.
## 2026-08-09 - BeautifulSoup Find-All Tag Matching Optimizations
**Learning:** For BeautifulSoup `find_all()` calls, passing inline lists (e.g., `["style", "script", "head"]`) causes repetitive memory allocation inside parsing loops which decreases performance significantly. Passing a pre-defined module-level constant tuple (e.g., `_TAGS = ('a', 'b')`) instead is measurably faster. In string heavy parsing environments like `ts4k`, pre-compiling simple repetitive patterns and caching them globally leads to reliable speed improvements. Furthermore, short-circuiting logic in element parsing (using early `if not` checks) avoids executing expensive regexes after a match condition is met. Combining independent regex search checks to limit BeautifulSoup DOM traversals from multiple passes into a single pass adds considerable speedups.
**Action:** When filtering tags in BeautifulSoup, always use module-level constant tuples for the `name` argument instead of inline lists. Combine regular expressions representing multiple classes of matches to reduce expensive DOM tree traversals, and always short-circuit DOM-property inspection loops early when a positive match has already been identified.
